## Adding or changing a project

Every project card lives in [`projects.json`](projects.json). The tabs and cards in `professional.html` and the selected projects in `cv.html` are generated from it.

1. Edit `projects.json`. Images go in `assets/projects/<slug>/`.
2. Run `python3 tools/build_site.py` to rewrite the generated blocks.
3. Run `python3 -m pytest -q tests` and commit. Without Playwright installed the browser checks are skipped; the next section shows how to run them.

A project can be `live`, `wip` (in progress) or `pending` (repository not public yet). Pending projects show on the Professional Log without links and stay off the recruiter view. `featured_order` decides which projects the recruiter view lists and in what order. A card can be opened directly with `professional.html#project-<slug>`.

## The terminal and the games

The desktop of the Professional Log has a Command Prompt (`cmd.exe`) and two games, Minesweeper and Jewels, also in the start menu. Most project cards have a ▶ button that opens the terminal and runs that project's demo. Each demo computes in the browser with a small slice of its repository's data and then checks itself against the numbers the project's own Python code produced:

| Command | Project | What runs in the browser |
|---|---|---|
| `macd` | macd-toolkit | EMA, MACD and PPO on three years of BTC/MXN closes, and how often the PPO crosses its signal |
| `btc` | macd-toolkit | Round-trip cost per platform and the three strategies of `btc_macd.py`, reproducing the recorded run to the cent. `btc mp BUY SELL` takes Mercado Pago's prices as its app writes them, for example `btc mp 1.503.231,35 1.487.661,56` |
| `qa` | incentive-comp-qa | The calculation test cases against build rc2, or rc1 with its rounding and gate defects (`qa rc1`) |
| `vigia` | vigia | The latency detector on a simulated day, with the calibrated rule or the old one (`vigia old`) |
| `notes` | class-notes-pipeline | BM25 with Spanish stemming over the sample note, as `extensiones/indice.py` ranks it |
| `api` | macd-signal-api | A `POST /v1/macd` response, a 422 and the BUG-M01 replay (`api bug`) |
| `retail` | Retail-Business-Data-Cases | Wilson intervals for 61 stores against their zone |
| `inflation` | inflation-reheating | The background equations of the thesis integrated with RK4, against SciPy |
| `reward` | reward-hacking-gsm8k | The three RL graders and the reasoning monitors on hand-written answers or on yours, against `posttrain/grading.py` and `monitors.py` |

Direct links: `professional.html?app=terminal&run=qa`, `professional.html?app=minesweeper`, `professional.html?app=jewels`.

The code lives in `assets/apps/` and loads the first time an app is opened. `demo-data.js` is generated by `tools/demo_data.py`, which needs the project repositories checked out next to this one (`--repos` points elsewhere) and computes every reference value with their own code. To add a demo, register it in the list at the end of `assets/apps/demos.js`, name it in the project's `demos` field in `projects.json` and run `python3 tools/build_site.py`. `build_site.py` rejects a card that names a demo the terminal does not have.

## How it is published

`.github/workflows/site.yml` runs on every push:

1. **Checks.** `build_site.py --check` validates `projects.json` (unique slugs, known tracks, images that exist, no card linking to another project's repository) and fails if a page is out of sync with it. The tests then confirm that every local link, image, cursor and script path resolves (the scripts the apps load included), that tags are balanced, that images declare alt text, that links opening a new tab use `noopener`, that no placeholder text is left and that the CV files are real PDFs.
2. **Browser and link checks.** Chromium, driven by Playwright, loads every page from a local server and fails on script errors, local files that do not load or images that do not decode. It also checks that `cv.html` and the case study fit a 390 px phone without sideways scrolling, that each project tab shows exactly its own cards, that every `professional.html#project-<slug>` link lands on its card, that each gallery window holds every image of its card and that the case study and the Professional Log link to each other. `test_apps.py` runs every demo and fails if any of them fails its own check. It also plays both games by their rules and opens the apps from every entry point. A last step confirms that every link and badge pointing at a GitHub repository answers 200.
3. **Publish.** Only on `main`, and only if both jobs pass, the site files are uploaded to GitHub Pages. Tools, tests and this README are not published.

To run everything locally:

```bash
python3 -m pip install -r requirements-dev.txt
python3 -m playwright install chromium
python3 -m pytest -q tests              # static, browser and link checks
python3 -m pytest -q tests -m "not network"   # offline
```

## Structure

```
├── index.html, professional.html, cv.html, qa-case-study.html, fun.html, 404.html
├── projects.json            Single source of truth for the project cards
├── assets/
│   ├── ui/                  Cursors, icons, GIFs, background and social card
│   ├── projects/<slug>/     Figures for each project
│   ├── qa/                  Newman HTML reports linked from the case study
│   ├── apps/                Terminal, project demos, Minesweeper and Jewels (loaded on demand)
│   └── cv/                  CV in English and Spanish (PDF)
├── tools/build_site.py      Validates projects.json and writes the generated blocks
├── tools/demo_data.py       Builds assets/apps/demo-data.js from the project repositories
└── tests/
    ├── test_site.py         Static checks on the HTML and projects.json
    ├── test_browser.py      The same pages loaded in Chromium
    ├── test_apps.py         The terminal, every demo and both games, in Chromium
    └── test_links_online.py Links to GitHub, checked over the network
```
